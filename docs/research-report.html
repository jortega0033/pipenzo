Research memo — AgentDock downstream product

The Implement Button

An open-source disruptor: a GitHub-issue-to-pull-request agent built on top of AgentDock, small enough on every PR to actually get reviewed.

Scope landscape · stack · pipeline · PR size · UI · model routing Method 10 parallel research agents, frontier model, primary sources License open source
Verdict

Build it, and win on the one axis every competitor is losing on: review burden. Agent PR acceptance is no longer catastrophically below human — the current best source, a task-stratified analysis of 7,156 agent PRs, puts it at Codex 77.9%, Cursor 74.5%, Claude Code 71.9%, Copilot 68.0%, Devin 61.6% (the earlier 55% vs. 82.6% figure this memo opened with is retired; see §11). What has not improved is the cost of trusting the output: review time rises 441.5% under heavy AI adoption, and 31% more PRs get merged unreviewed — because every incumbent optimizes for how much an agent can ship, not how cheaply a human can trust it.

State the thesis as the bet it is. That same dataset finds acceptance tracking task type — chore 84.0%, docs 82.1%, feature 66.1%, fix 66.0%, perf 55.4% — and does not analyze acceptance against diff size at all. So "small PRs get accepted more" is not an established finding; it is a design bet, defensible on review-burden grounds rather than acceptance-rate grounds, and this memo should not launder one into the other. The plan now hedges accordingly: the diff-size gate is paired with task-type-aware routing (§08, near-term post-MVP), because task type is the variable the evidence actually shows moving the number.

The app is scoped against review burden regardless: every PR it opens is small enough to review in one sitting, by construction — gated at the planning step, not chopped after the fact — reviewed first by deterministic tools and a cross-model adversarial pass before a human ever sees it, and usable by a non-developer without ever reading a diff. AgentDock supplies the plumbing underneath — worktree isolation, session resume/fork, an approval and audit model, an SSE event stream — which is what the module table in §07 accounts for row by row.

02

The correction — and the real wedge

re-check

A first pass called Alfred "CLI/config-only." A deeper read of its actual source found a signed, six-tab desktop app with a working kanban and approve/decline UI — a direct competitor to the original pitch, not an absence to build into.

Sources: DESKTOP_CLIENT.md, PipelineView.tsx (github.com/luminik-io/alfred)

So "nobody has a UI" doesn't hold. What does hold, on the same close read: Alfred's "team" is a set of role slugs fired by launchd/systemd on fixed cron intervals — it explicitly rejects a persistent orchestrator as a design goal, and its roles never share state across repos. Sortie's own maintainer has stated, in a public discussion, that an interactive UI is not the roadmap.

AgentDock's daemon is already long-lived. That's the wedge that survives scrutiny: on-demand dispatch with live SSE streaming, on a Windows-first Electron shell — not "has a UI," but "has a UI backed by a runtime built to stay running," which is structurally outside what either close competitor is aimed at.

One correction to the wedge as first written: "cross-platform" is a claim about the architecture, not about what v1 distributes. AgentDock's electron-builder.yml targets Windows x64 NSIS only, unsigned, with publish: null and no auto-update — Pipenzo inherits exactly that. Against Alfred's macOS-only signed app, "runs where Alfred doesn't" is therefore a statement about Electron plus a Node daemon having no platform-specific assumptions in the loop, not about a macOS or Linux build existing. macOS is post-MVP and needs a paid Apple Developer ID and notarization; see the README's Packaging & distribution section, where this is a stated decision with its adoption cost named.

03

The stack

AgentDock's apps/desktop has zero UI runtime dependencies today — roughly 1,650 lines of hand-written CSS across two stylesheets, no component library. Every pick below was checked against that renderer's actual constraints: a strict CSP (style-src 'self' unsafe-inline', no external script hosts), contextIsolation + sandbox, and a daemon that's esbuild-bundled to one file and run under Electron's own Node ABI — which rules out native addons.

not daisyui

DaisyUI was the starting suggestion. It's ruled out for one specific reason: it hands you CSS classes for markup you still write — it can't manage focus or announce state changes, so the approval dialog (where a non-developer says yes to something irreversible) would need a headless library bolted on anyway. shadcn/ui gives you the component source, owned in-repo, built on Base UI primitives that already solve focus-trapping and ARIA. That's the whole decision: a dual-audience UI is a structural problem, not a styling one — a PM needs one sentence and a button, a developer needs the branch name and the raw diff, and you can't express that difference in daisyUI's class names.

shadcn/Base UI registry components target React 19; AgentDock's desktop is on React 18.3 — tracked upstream as agentdock#106. Approved, with one sequencing condition: primitive components, design tokens, and branding get established first, before any product screen is built against them — not screen-by-screen improvisation.

04

Plan, refine, implement, review

The instinct was to reach for a multi-agent framework — Agency Swarm, LangGraph, CrewAI. All three would duplicate machinery AgentDock's daemon already runs.

no framework

AgentDock's daemon already negotiates session.fork, tracks a durable parent/child subagent graph, and gates every consequential action through one permission policy with a full audit trail. That's the same differentiator LangGraph sells. Adding a second orchestrator on top means two sources of truth for cancellation, permissions, and resume. The pipeline below is a thin state machine inside the daemon, driving scoped subagent definitions — no new runtime.

05

Model routing

The app should route each phase to a model tier by task complexity, not run everything on one frontier model — and orchestrate across providers deliberately, not just within one. AgentDock already wraps Claude and Codex; Gemini is next on its own roadmap. The routing policy below is written as tiers and vendors, not hardcoded model names, so a third provider slots into the same table rather than requiring a redesign. A verification pass found the wire support for this doesn't exist in AgentDock yet.

resolved

This box previously said the wire support didn't exist. It does now — agentdock#107 landed. POST /v2/sessions takes an optional validated model (packages/shared/src/protocol-v2.ts), and the model catalog is served for real at GET /v2/providers/:providerId/models (apps/daemon/src/routes/v2-providers.ts). Per-phase model selection is unblocked.

The real remaining constraint is a different one, and it is not going away: a continuation freezes the model. The fork/resume input accepts a model only to re-assert the parent's frozen value; the daemon compares it against the continuation scope's selectedModel and rejects a mismatch as continuation_scope_mismatch, because a provider-native thread cannot switch models mid-run. That is correct behaviour, not a bug to file — but it means the escalation column below cannot be implemented as "fork at a higher tier". Every tier escalation is a fresh session. The ladder in the table is written that way.

Read from AgentDock's source directly rather than from an issue tracker: protocol-v2.ts, v2-session-facade.ts, routes/v2-providers.ts.

A note on "tier", which was doing two jobs. A routing class is a phase of work (the left column); a model tier is a model's strength (the second column); the kanban lanes in §08 are a third, unrelated thing. The three are kept distinct from here on.

Why the reviewer is exempt and the verifier is not. The reviewer is advisory — its findings feed the implement retry, they never gate anything — so it may run below the implementer's tier without risk. The verifier is the gate, and never may. The cross-tier regression evidence below is specifically about gating review; advisory findings that a same-or-higher-tier verifier subsequently adjudicates do not carry it.

Deterministic overrides force the frontier tier before the estimate is even consulted: any prior failed attempt, paths matching security/auth/migration globs, a priority:high/breaking label, or more than 8 files touched and more than 100 changed lines. The file-count clause is conjunctive deliberately — a bare ">8 files" override contradicted §06's ≤ 10 files single-PR allowance, forcing the frontier tier onto tickets the size gate calls small. The estimate from the refine phase is the routing signal — a dedicated classifier step was considered and rejected: deployed routers rarely beat an oracle by much, and per-task difficulty often isn't predictable from the prompt alone, which is exactly what the deterministic overrides exist to catch.

Guardrails against slop and hallucination aren't a separate system — they're what this whole pipeline is for. Low quality is caught by the deterministic gates and the tier-up adversarial verifier before a human ever sees it; fabrication is refused at the source — the verification block cites only what a gate actually produced (a real test run, a real diff stat), never an unearned claim, and anything self-reported is labelled as such rather than presented as fact. What's new here: a humanizing rewrite pass — a cheap-tier style transform, a real step in the pipeline rather than a hope that a good prompt handles it — so generated prose reads like a careful colleague wrote it, not templated AI output. It is scoped narrowly, and the scope is the load-bearing part: it applies to non-evidential prose only — the drafted issue body in Plan and the plain-language summary in Simple mode. It never touches the verification block, gate results, diff stats, or pre-commitment records, all of which are rendered from data. A style pass over an evidential claim is a mechanism for drifting facts, which is precisely what the rest of this pipeline exists to prevent, so the two must not be allowed to meet. It carries this scope in §08's MVP list rather than living only in this paragraph.

The verifier rule is deliberately route up, never sideways or down — a 116-task cross-model study found the weaker model reviewing the stronger one caused net regressions (3 fixes, 13 new bugs introduced), while the stronger reviewing the weaker gained +18.1pp. Vendor diversity only breaks ties between reviewers of equal strength. Two more review-quality rules follow from separate evidence: the reviewer session sees only the spec and the diff, never the implementer's own transcript — same-session self-review measurably underperforms a fresh session seeing just the artifact; and tests are generated from the spec by a different pass, never written by the implementer itself, since self-authored tests are contaminated by the code they're meant to check.

One unit, one total order — this table used to have holes. The earlier rows read "≤ 100 lines / 100–400 lines / > 500 additions", which left 400–500 matching no row at all, and mixed lines against additions as though they were the same measurement. The unit is now changed lines (additions + deletions) and files touched, with whichever of the two is worse selecting the row — so every estimate lands in exactly one.

And a blown estimate has a consequence, which it previously didn't. The estimate is re-checked against the real diff at Review. A final diff exceeding its estimate by more than 50% does not quietly open a PR anyway: the ticket enters pipenzo:awaiting-stack-approval showing predicted against actual, and the miss is recorded on the ticket. An estimate nothing is ever graded against is a suggestion, not a gate — and the recorded misses are what the classifier's calibration gets measured from.

The risk classifier, and what it maps

LOW/MEDIUM/HIGH does not classify itself, and it cannot be the agent's own judgment — an agent grading its own actions is not a gate. It is a daemon-side module whose job is translating AgentDock's real permission taxonomy into Pipenzo's three levels. AgentDock grades an action on two axes: an actionClass of filesystem | command | network | mcp | external_side_effect | other, and a risk of normal | destructive | unknown (packages/shared/src/policy-v2.ts). The mapping:

Pipenzo levelFrom AgentDock
LOWrisk: normal, actionClass of filesystem or command, and a path inside the ticket's own worktree.
MEDIUMEverything AgentDock routes to ask that is not external_side_effect.
HIGHexternal_side_effect, a destructive MCP tool (mcpDestructive), or a path matching the security/auth/migration globs already used for tier override in §05.

One classifier serves both risk grading and the pre-commitment trigger. The "roughly 95% of actions should be LOW" target in §11 item 05 is a measured figure — asserted in a fixture-corpus test, not in prose.

The ticket store — schema, and which source of truth wins

Eleven-plus features here need persisted per-ticket state, so the shape is written down rather than left as "a JSON file store". It follows AgentDock's FileSessionStore pattern: one JSON file per record, a manifest.json carrying schemaVersion, atomic writes. Fields: ticketId, repo, issueNumber, lane, phase, labels[], estimate{lines,files,layered}, stack{parentId,childIds[],index}, worktree{id,path,branch}, attempts[{sessionId,tier,model,outcome}], budget{tokensUsed,limit}, risk{score,lastResetAt}, precommits[{action,expect,ifWrong,outcome,verdict}], etags{issues,pr,checks}, schemaVersion. attempts[] is what carries lineage across a tier escalation, where the provider thread does not; etags is what makes a 30-second poll affordable.

There are two stores by design, so there is one precedence rule. GitHub labels are authoritative for a ticket's lane. The JSON store is authoritative for everything GitHub cannot hold — worktree id and path, session and attempt lineage, budget consumed, risk score, pre-commitment events, poll ETags. On divergence about a lane — a teammate dragged the card on github.com, a crash landed mid-write — the disagreement is written to the audit store and the label wins; the local record reconciles to it, never the reverse. Without that rule, "labels as the state model" and "a JSON ticket store" are simply two sources of truth with no tiebreak.

And a claim, because polling answers latency but not simultaneity. Two teammates can both press Implement inside one poll window. The claim is GitHub issue assignment — the one piece of per-issue state GitHub already arbitrates: Implement assigns the issue to the authenticated user and refuses to start if it is already assigned to someone else, with an uncached GET /issues/:n immediately before dispatch rather than a read from the poll cache. That narrows the window to a round-trip and kills the realistic race. It does not kill the theoretical one and should not claim to: GitHub offers no compare-and-swap on labels or assignees, so this is best-effort, not a mutex. The loser parks to Needs-human with "claimed by @someone-else" rather than diverging silently.

Build order

Design system, before any screen

Establish shadcn/ui's primitive components, design tokens (color, type, spacing), and branding first — the walking skeleton and everything after builds against this, not around it.

Walking skeleton

Hardcoded repo, PAT from env, no queue, built against the design system above. One ticket through refine (EARS spec + size estimate) → implement → deterministic + adversarial review → react-diff-view screen → Open PR. Proves the loop end to end before anything else exists.

Ticket store + phase machine over labels

JSON-file persistence matching AgentDock's existing store pattern, phase-change SSE, a real ticket detail/progress view, and the dirty-worktree discard path. The GitHub client lands here, not at step 4 — a phase machine whose states are GitHub labels cannot write a state without one. Only the client; OAuth stays at step 4 and this step keeps reading a PAT from env, as step 2 does.

Crash recovery is two problems, and only one of them was specified. The ticket store's own recovery is the easy half. The other half: AgentDock's recoverInterruptedExecutions() marks interrupted sessions failed and reports their ids — it does not auto-resume or auto-retry them (apps/daemon/src/execution-graph-store.ts, apps/daemon/src/session-store.ts). So a daemon crash mid-Implement leaves an interrupted session, a dirty worktree, and a ticket whose local phase and GitHub label disagree — with nothing owning the reconciliation. On daemon start Pipenzo reads the recovery report's interrupted session ids, maps each to its ticket, and moves that ticket to pipenzo:interrupted in the Needs-human lane showing the last completed phase and the worktree path, offering exactly two actions: resume — offered only when a providerSessionId and a continuationScope both exist, i.e. only when it will actually succeed — or discard and restart. It never auto-resumes: the approval state of an in-flight MEDIUM or HIGH action is unknowable after a crash, and resuming into one would re-run something a human may have been about to deny. This is also why the dirty-worktree discard path moved here from step 6 — a crashed session's worktree is dirty by definition.

GitHub auth & the size gate, properly

Device-flow OAuth (@octokit/auth-oauth-device) in Electron main, token vault, real issue list, the diff-size/split gate enforced at refine, a test asserting the token never reaches a provider subprocess. The @octokit/core client itself already exists from step 3; what lands here is real authentication in place of the PAT-from-env, plus rate-limit handling (ETags, throttling, retry) now that polling is real.

Queue + dual-audience mode + bounded concurrency

dnd-kit kanban, simple/expert toggle with a persisted default, built on the established design system. Multiple tickets queued, one worktree each, respecting the existing workspace-execution lease — and a concurrency semaphore in the ticket orchestrator (default 2, hard cap 4) that serialises any two tickets whose Refine-phase "files likely touched" lists overlap. Worktree provisioning is serialised in the orchestrator too, with a retry on worktree_busy — AgentDock's worktree manager throws rather than queues when two provisioning calls hit one source repo concurrently, so concurrency without that serialisation fails on its first real double-start.

Polish

Native notification on HIGH-risk approvals (plus the 60-second escalation on an unanswered MEDIUM), a rejection loop that forks implementation again, the risk classifier specified in §07, terminal-state worktree cleanup with its dirty-refusal surface and git branch -D sweep, an audit entry for every publish and every review-gate result. The dirty-worktree discard path is no longer here — it moved to step 3, where the crash reconciler needs it.

First post-MVP milestone

gh stack publishing for approved decompositions, then CI-failure auto-fix — one forked attempt, classifiable failures only, re-entering the same human push gate. Both are committed with triggers, not "later" (§11 decisions 06–07).

watch The biggest risk is step 2's temptation to let the agent shell out to gh directly — step 2, the walking skeleton, because step 1 is the design-system step and has no agent in it at all. Keep publishing outside the agent loop from the first commit — retrofitting that boundary later is what breaks the safety property this whole design depends on.

08 Persistent repo knowledge baseout of scopeOut — and this is a judgment, not a deferral. A durable knowledge base adds an index, an invalidation strategy, an embedding store, and a staleness problem whose failure mode is an implementer confidently misled by an out-of-date wiki — worse than having none. One correction to that argument, because it was leaning on something unowned: the fresh symbol graph is not a Pipenzo component either. AgentDock has no symbol index, tree-sitter parser, or LSP client anywhere in it (verified by grep against the repository), and Pipenzo builds none — the graph comes from a user-configured stdio MCP server, inherited exactly as decision 09 describes, with a Grep/Glob fallback when none is configured. So the accurate decision is: Pipenzo declines to own a durable index, and consumes a per-session graph when the user has configured a server that provides one. This is the cheaper and more honest resolution than inventing a daemon-side symbol-graph module, and it keeps faith with decision 09's "Pipenzo adds no MCP UI of its own." The consequence is stated rather than hidden: on a default install with no such server, the +12.2% figure is not what the user gets. DeepWiki and Librarian are indexing products with staff and infrastructure behind them; Pipenzo deliberately has a JSON file store, no DB, and no native addons (§03 rejected better-sqlite3 for precisely this class of reason). The human-gated lesson memory already on the roadmap is the intentional small substitute: append-only, human-approved, no index.
09 MCP integrationout of scope as a Pipenzo featureOut — because it already exists one layer down. AgentDock ships a trusted local-stdio MCP catalog with a route-level approval gate, workspace-trust revalidation, and fail-closed destructive-tool classification (agentdock#85). Any server a user wants is configured at the runtime and inherited; Pipenzo adds no MCP UI and curates no servers. Jules' comparables (Linear, Neon, Stitch) are hosted/HTTP — a transport AgentDock explicitly does not support, so matching them means new runtime transport work, not a Pipenzo feature. And the one integration that matters for this loop, GitHub, is actively contraindicated as an MCP server: it would put the token inside the agent process and break the property §07 rests on — publishing is a daemon-side service the agent process cannot call. One consequence worth noting rather than a gap: because AgentDock's classification is fail-closed, any MCP tool a user does attach lands at HIGH in the risk grading below unless the server declares otherwise, so it inherits the approval UI for free.

The five committed items, specified

Previously these were named as gaps but never designed. Each is now a buildable spec, written against the six screens on the design canvas.

01 · Diff-size gate — refusal as a state, stacks handed to GitHub

MVP

The gate produces two ticket states, not an error, both backed by GitHub labels and both landing in the existing Needs-human lane. pipenzo:needs-pre-scoping — the agent declined; the card shows the estimate, which threshold tripped, and the proposed split, presented as a finished outcome. Nothing retries it automatically. pipenzo:awaiting-stack-approval — a 2–4 PR decomposition is waiting for a human to accept, reorder, or reject; approving materialises one dependency-ordered child ticket per entry, each with its own worktree and branch, and the parent becomes a container card showing 1/3, 2/3 progress. Devin decomposes but never asks; the approval step is the part that stays unclaimed.

Maintenance is delegated, not built. Pipenzo owns the split decision, the ordering, and the human approval of it. GitHub owns base-branch rewriting, restacking after a merge, and the PR-to-PR view, via native stacked PRs and the gh stack CLI — invoked from the daemon-side publish service under the same execFile trust model as git, never as an agent tool. This is a deliberate exception to §03's "not the gh binary" rule and the only one: the API client stays @octokit/core, and gh is runtime-detected and optional. Without it an approved stack still ships, as sequential PRs with an explicit base-branch note. Pipenzo renders the stack as a read-only list linking out to GitHub's own stack view, and never writes a restacker.

02 · Pre-commitment — predict, then be graded on it

MVP

When: before every action graded MEDIUM or HIGH by the classifier in item 05. LOW actions do not pre-commit — the point is a readable signal, not a transcript of every file read. One classifier serves both features.

What the implementer posts, as a structured precommit event, before the action runs: the action verbatim; expect — one sentence predicting the outcome ("the three new cases in provider-caps.test.ts pass, nothing else changes"); if_wrong — what it will do if the prediction fails. The real result is appended afterwards as a paired outcome event and diffed against the prediction into a match / partial / mismatch verdict.

In the event stream (TicketDetail → Activity): the prediction lands first as its own row, marked predicted. When the outcome arrives the pair collapses to a single row carrying matched or mismatched. Mismatched pairs never auto-collapse. This is the part worth having: pre-commitment is usually an internal anti-fabrication trick, and exposing the mismatch count turns it into something a reviewer can act on — the PR body's confidence line degrades when it is non-zero ("the agent's own predictions were wrong twice during this run"), Simple mode says the same in plain language, and each mismatch feeds the cumulative-risk counter. An agent whose predictions are going wrong gets checked on sooner, automatically.

03 · Screenshot verification — legible, and still not proof

MVP

How it is captured: Playwright, driven by the daemon, using the target repo's own installation. Pipenzo ships no browser and detects the capability rather than providing it — if the worktree has @playwright/test and a dev or preview script, the verification phase runs a capture the daemon drives itself (start the dev server on an ephemeral localhost port, navigate, capture, tear down). Repos without Playwright can set a pipenzo.verify.screenshot command that emits PNGs to a directory. Neither available means the evidence block says so — there is no fallback and nothing is faked. A baseline capture on the base commit before implementation gives a genuine before/after pair, which is what makes the screenshot mean something rather than decorate; its cost — a second checkout and a second dev-server run per ticket — is counted against the per-ticket budget rather than treated as free, and the capture step takes the execution slot serially so two concurrent captures cannot collide on a port.

Corrected: the agent does not write the capture script. This item originally specified "a short capture script generated from the spec's EARS clauses", run by the daemon. That is a security regression, and a serious one: the daemon is the process holding the token-vault boundary, and executing agent-authored automation inside it hands the agent arbitrary code execution next to the token — destroying the exact property (the agent never touches the token) that §07 and decision 09 both rest on. Rejecting Electron's webview for putting an untrusted page near the vault, while accepting agent-generated code inside the daemon, was not consistent.

The design is now a declarative capture manifest. The agent proposes data, not code: {route, viewport, waitForSelector, actions: [{click|fill, selector, value}]}, validated against a schema before anything runs. The daemon owns every actual Playwright call, and navigation is restricted to the ephemeral localhost origin the daemon itself started. No agent-generated JavaScript executes in the daemon, ever. The manifest is expressive enough for the real cases — a route, a viewport, a login fill, a click to open the panel being screenshotted — and unable to express anything else, which is the point. The pipenzo.verify.screenshot escape hatch stays free-form, and that is not an inconsistency: it is repo-authored and human-committed, so a person reviewed it before it ever ran, the same trust class as the repo's build script. Agent-authored-at-runtime and human-committed-in-the-repo are different things, and only the first is the problem.

Two alternatives stay rejected, for the record: the agent driving a browser itself (arbitrary network egress inside the agent process), and Electron's own webview (running the target app inside the renderer that holds the token vault and the hardened CSP).

Where it renders: DiffReview's existing Verification block gets a thumbnail strip, each shot captioned with the EARS clause it was captured for plus URL, viewport, and commit SHA. Simple mode makes it the hero — the before/after pair above the plain-language summary, because for the non-developer audience this is the evidence. The PR body carries the same images with the same captions.

How it stays honest: a screenshot feels like proof and isn't — the agent chose the URL, the state, and the moment. So the verification block splits into two visually distinct zones that are never merged into one list: machine-verified (build, typecheck, spec-generated tests, gitleaks, Semgrep — results the app produced) and agent-captured, self-reported (text evidence and every screenshot). Each shot carries a fixed provenance line rather than a subtle badge — "captured by the agent, showing what it chose to show" — with the capture manifest expandable beside it, so a human can read exactly which route, viewport, and interactions produced the image. Hard rule: a screenshot is never an input to a pass/fail decision. It buys legibility, not trust.

no UI impact

05 · Risk-graded approval, with cumulative risk

MVP

Three levels, classified per action, replacing the single approve/reject card:

LOW Reversible, inside the owned worktree, no network, no secrets — reads, greps, edits to source under the worktree, running the repo's own build and test commands. Auto-proceeds. No card, no notification, one passive line in the Activity stream. This should be roughly 95% of actions; if it isn't, the classifier is wrong.

MEDIUM Reversible but consequential, or outside the obvious blast radius — adding a dependency, running a script not declared in the repo's manifest, writing outside the source tree (lockfiles, CI config, .github/), deleting files, rewriting local history, network egress for a package fetch. Blocks on a compact inline card in the Activity stream: approve, or reject with a reason. Requires a pre-commitment record. No OS notification unless it has been waiting more than 60 seconds — a MEDIUM that resolves in a few seconds should not interrupt anyone, but one silently blocking the whole run for an hour is exactly what notification is for. (The README states the rule in the same terms; the two no longer disagree.) Undo, defined: it restores the paths the action touched from the pre-action worktree state, and is valid until the next commit on that branch. Filesystem actions only — and never HIGH, per below.

HIGH Irreversible or off-machine — anything AgentDock classifies external_side_effect (push, open PR, comment on the issue), paths matching the security/auth/migration globs already used for tier override in §05, force-push, deleting outside the worktree, writing a credential-shaped string, and any MCP tool not explicitly declared safe. The full approval card, OS notification, mandatory reason on reject. The existing rule is unchanged and unchangeable: no persistent auto-allow exists for external_side_effect at any risk level, and Undo does not apply — once approved it has left the machine.

Cumulative risk — yes, and it is the interesting half. OpenHands' actual insight is that risk compounds across a session even when every individual step is fine, so the counter tracks unreviewed accumulation rather than total severity. The weights and the reset rule are both revised, because the first version could not reach its own threshold. Under "any approval resets to zero", a MEDIUM or HIGH action is immediately followed by its own approval, which wipes the counter before its weight can accumulate — so only LOW actions could ever add up, and at +0.1 each the stated example ("14 low-risk actions") came to 1.4 against a threshold of 10. The copy described something the arithmetic made impossible.

Corrected: each auto-approved LOW action adds 0.5, each MEDIUM approval adds 1, each pre-commitment mismatch adds 3, a HIGH action adds nothing (a human already looked hard at it). Threshold 10. Only a HIGH approval — or an explicit "I've looked", meaning opening the ticket's Activity view — resets the score to zero. A MEDIUM approval deliberately does not: approving one inline card is a glance at one action, not a review of the run, and treating the two as equivalent is what broke the original formula. The example now works out as written: 14 low-risk actions (7.0) plus a single prediction mismatch (10.0) trips it. When the score crosses the threshold the next MEDIUM action is promoted to HIGH — full card, notification — and the card states why: "14 low-risk actions since your last look." It renders in TicketDetail's right rail beneath Budget and Subscription headroom, in the same visual language: a segmented bar reading ok → building → check in. It is a "since you last looked" meter, not a threat gauge.

A second independent pass — the "4 layers of AI code review"

Run separately from the CodeRabbit research that produced decisions #283 and #284 above, against a walkthrough of the industry's own "4 layers of AI code review" framing (youtube.com/watch?v=As2xy_cSx00). The result this time is not a gap or a differentiator — it is a convergence, and the same honesty standard this addendum holds itself to for a discovered gap applies to admitting when a comparison finds nothing new: every one of the four layers already exists in Pipenzo's shipped plan, under names this report already used.

1 · Automate the obvious

shipped

Lint, typecheck, format, tests and security scanning as deterministic hooks, gating before anything else runs. Pipenzo's own deterministic gate set — review-gates.ts, issue #181 — now includes lint alongside build, typecheck, gitleaks and Semgrep (#283).

2 · Local AI review

shipped

An agent reviews the diff against project-specific criteria stated in a repo-owned file, not just generic taste. README's Review-phase LLM reviewer and adversarial verifier are this layer, and issue #284's repo-authored conventions file — a maintainer states norms once in package.json's pipenzo key, folded into both passes' prompts — converges independently on the same review.md-shaped practice the video itself argues for.

3 · Automated safety net

spec ready

A GitHub-side check that runs whether or not a human remembered to review locally — a backstop independent of the first two layers, not a repeat of them. The External PR Review epic (issue #208, #205–#207) is exactly this, already spec: ready, and arguably more disciplined than the video's version: human-gated post-back rather than a fully automatic comment.

4 · Human review, scaled by risk

shipped

The layer that decides how much of a human's attention each change actually earns. Decision 05 above — LOW/MEDIUM/HIGH risk grading with a cumulative-risk counter that promotes the next action when unreviewed work piles up — is this layer, specified in this same document.

Nothing here is a new mechanism or a new commitment — it is an already-built architecture getting a name a reader outside this repository will already recognize.
