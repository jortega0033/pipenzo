Research memo — AgentDock downstream product

The Implement Button

An open-source disruptor: a GitHub-issue-to-pull-request agent built on top of AgentDock, small enough on every PR to actually get reviewed.

Scope landscape · stack · pipeline · PR size · UI · model routing Method 10 parallel research agents, frontier model, primary sources License open source
Verdict

Build it, and win on the one axis every competitor is losing on: review burden. Industry-wide, agent PR acceptance sits at 55% against 82.6% for humans and review time rises 441.5% under heavy AI adoption — because every incumbent optimizes for how much an agent can ship, not how cheaply a human can trust it. A near-identical funded competitor, Sweep.dev, discontinued this exact product chasing that same metric.

This app is scoped against the metric that actually matters instead: every PR it opens is small enough to review in one sitting, by construction — gated at the planning step, not chopped after the fact — reviewed first by deterministic tools and a cross-model adversarial pass before a human ever sees it, and usable by a non-developer without ever reading a diff. AgentDock already supplies roughly 60% of the plumbing — worktree isolation, session resume/fork, an approval and audit model — for the rest.

02

The correction — and the real wedge

re-check

A first pass called Alfred "CLI/config-only." A deeper read of its actual source found a signed, six-tab desktop app with a working kanban and approve/decline UI — a direct competitor to the original pitch, not an absence to build into.

Sources: DESKTOP_CLIENT.md, PipelineView.tsx (github.com/luminik-io/alfred)

So "nobody has a UI" doesn't hold. What does hold, on the same close read: Alfred's "team" is a set of role slugs fired by launchd/systemd on fixed cron intervals — it explicitly rejects a persistent orchestrator as a design goal, and its roles never share state across repos. Sortie's own maintainer has stated, in a public discussion, that an interactive UI is not the roadmap.

AgentDock's daemon is already long-lived. That's the wedge that survives scrutiny: on-demand dispatch with live SSE streaming, on a cross-platform Windows-first Electron shell — not "has a UI," but "has a UI backed by a runtime built to stay running," which is structurally outside what either close competitor is aimed at.

03

The stack

AgentDock's apps/desktop has zero UI runtime dependencies today — 1,246 lines of hand-written CSS, no component library. Every pick below was checked against that renderer's actual constraints: a strict CSP (style-src 'self' unsafe-inline', no external script hosts), contextIsolation + sandbox, and a daemon that's esbuild-bundled to one file and run under Electron's own Node ABI — which rules out native addons.

not daisyui

DaisyUI was the starting suggestion. It's ruled out for one specific reason: it hands you CSS classes for markup you still write — it can't manage focus or announce state changes, so the approval dialog (where a non-developer says yes to something irreversible) would need a headless library bolted on anyway. shadcn/ui gives you the component source, owned in-repo, built on Base UI primitives that already solve focus-trapping and ARIA. That's the whole decision: a dual-audience UI is a structural problem, not a styling one — a PM needs one sentence and a button, a developer needs the branch name and the raw diff, and you can't express that difference in daisyUI's class names.

shadcn/Base UI registry components target React 19; AgentDock's desktop is on React 18.3 — tracked upstream as agentdock#106. Approved, with one sequencing condition: primitive components, design tokens, and branding get established first, before any product screen is built against them — not screen-by-screen improvisation.

04

Plan, refine, implement, review

The instinct was to reach for a multi-agent framework — Agency Swarm, LangGraph, CrewAI. All three would duplicate machinery AgentDock's daemon already runs.

no framework

AgentDock's daemon already negotiates session.fork, tracks a durable parent/child subagent graph, and gates every consequential action through one permission policy with a full audit trail. That's the same differentiator LangGraph sells. Adding a second orchestrator on top means two sources of truth for cancellation, permissions, and resume. The pipeline below is a thin state machine inside the daemon, driving scoped subagent definitions — no new runtime.

PhaseMechanismEvidence
Plan (new)The pipeline above assumed a GitHub issue already exists — it doesn't have to. A conversational brainstorm with an agent turns a rough idea into a real issue: the human describes a problem in plain language, the agent asks clarifying questions, then drafts and — on confirmation — creates the actual GitHub issue via the API. This is also the on-ramp for the non-developer audience, who may never have written an issue at all. The new ticket then enters Queued like any other.Closes a real gap: every phase after this one assumed intake was solved

Missing or oversized → stop and ask a human here, while it's cheap.Kiro / Spec Kit spec-driven pattern
ImplementFresh session seeded only with the spec plus symbol-graph context from a codebase-memory tool (not raw file search). 05

Model routing

The app should route each phase to a model tier by task complexity, not run everything on one frontier model — and orchestrate across providers deliberately, not just within one. AgentDock already wraps Claude and Codex; Gemini is next on its own roadmap. The routing policy below is written as tiers and vendors, not hardcoded model names, so a third provider slots into the same table rather than requiring a redesign. A verification pass found the wire support for this doesn't exist in AgentDock yet.

prerequisite

POST /v2/sessions has no model field today — the schema is .strict() and a caller passing one gets rejected. The internal plumbing to run a specific model exists, but it's fed only from provider auto-detection, never from a request. Filed upstream as agentdock#107: add an optional, validated model field to session creation and resume/fork, and serve the already-declared-but-unimplemented model.catalog capability for real.

PhaseTierDeciding signalEscalation
Refinemid, fixedNever cheapened — the spec is the contract everything downstream is graded againstFails validation → 1 retry same tier; then human
Implement — smallcheapEstimate ≤ 50 LOC, ≤ 2 files, no prior retryGate failure → retry same tier ×1, then ↑1 tier ×1, then human
Implement — standardmidDefault, ≤ 300 LOC / ≤ 8 filesSame ladder, capped at 3 attempts
Implement — hardfrontierAbove standard, or a deterministic override1 retry with telemetry, then human — no auto-escalation
Review — reviewermid, same vendor as implementFixedFindings feed the implement retry, not a new model
Review — adversarial verifier≥ implement's tier, never lowerCross-vendor as a tiebreaker among equal tiers onlyRejects twice → human, verifier itself never escalates

Deterministic overrides force the hard tier before the estimate is even consulted: any prior failed attempt, paths matching security/auth/migration globs, more than 8 files touched, or a priority:high/breaking label. The estimate from the refine phase is the routing signal — a dedicated classifier step was considered and rejected: deployed routers rarely beat an oracle by much, and per-task difficulty often isn't predictable from the prompt alone, which is exactly what the deterministic overrides exist to catch.

Guardrails against slop and hallucination aren't a separate system — they're what this whole pipeline is for. Low quality is caught by the deterministic gates and the tier-up adversarial verifier before a human ever sees it; fabrication is refused at the source — the verification block cites only what a gate actually produced (a real test run, a real diff stat), never an unearned claim, and anything self-reported is labelled as such rather than presented as fact. What's new here: every piece of text the app generates for a human — the drafted issue in Plan, the PR description, the plain-language summary in simple mode — passes a humanizing rewrite pass before it's shown, so it reads like a careful colleague wrote it, not templated AI output. That's a real, separate step in the pipeline (a cheap-tier pass, since it's a style transform, not a judgment call), not a hope that a good prompt handles it.

The verifier rule is deliberately route up, never sideways or down — a 116-task cross-model study found the weaker model reviewing the stronger one caused net regressions (3 fixes, 13 new bugs introduced), while the stronger reviewing the weaker gained +18.1pp. Vendor diversity only breaks ties between reviewers of equal strength. Two more review-quality rules follow from separate evidence: the reviewer session sees only the spec and the diff, never the implementer's own transcript — same-session self-review measurably underperforms a fresh session seeing just the artifact; and tests are generated from the spec by a different pass, never written by the implementer itself, since self-authored tests are contaminated by the code they're meant to check.

Small PRs, by construction

None of Alfred, Sortie, or OpenHands has any diff-size budget today — checked their docs directly, zero hits. Devin ships stacked PRs but decomposes by architecture, not a published number. A measurable, enforced budget is unclaimed ground.

08

Build order

Design system, before any screen

Establish shadcn/ui's primitive components, design tokens (color, type, spacing), and branding first — the walking skeleton and everything after builds against this, not around it.

Walking skeleton

Hardcoded repo, PAT from env, no queue, built against the design system above. One ticket through refine (EARS spec + size estimate) → implement → deterministic + adversarial review → react-diff-view screen → Open PR. Proves the loop end to end before anything else exists.

Ticket store + phase machine

JSON-file persistence matching AgentDock's existing store pattern, crash recovery, phase-change SSE, a real ticket detail/progress view.

GitHub & the size gate, properly

Device-flow OAuth (@octokit/auth-oauth-device) in Electron main, token vault, real issue list via @octokit/core, the diff-size/split gate enforced at refine, a test asserting the token never reaches a provider subprocess.

Queue + dual-audience mode

dnd-kit kanban, simple/expert toggle with a persisted default, built on the established design system. Multiple tickets queued, one worktree each, respecting the existing workspace-execution lease.

Polish

Native notification on "awaiting approval," a rejection loop that forks implementation again, a dirty-worktree discard path, an audit entry for every publish and every review-gate result.

watch The biggest risk is step 1's temptation to let the agent shell out to gh directly. Keep publishing outside the agent loop from the first commit — retrofitting that boundary later is what breaks the safety property this whole design depends on.

Competitive positioning — addendum, September 2026

Added after the plan was first drafted and after the design canvas was built, to check the plan against what shipped competitors actually do today rather than at the time of the original ten research passes. Primary sources only — vendor docs, changelogs, one peer-reviewed dataset — cited per claim below.

headline Two of the plan's three claimed differentiators shipped elsewhere in the first half of 2026. The diff-size-thesis is intuitive but not established by the best available evidence — acceptance rate tracks task type, not diff size.

Where the plan is genuinely ahead

Refusal as an outcome

still unique

Devin decomposes into stacks at plan time and announces the stack by name, but ships no size thresholds, no refusal condition, and no human approval of the decomposition. Pipenzo's numeric gate (≤100 / 100–400 / >500 lines) with a hard refuse-and-flag branch is still unmatched — the mechanism is commoditized, the policy isn't.

Same-or-higher-tier verifier

undocumented elsewhere

Jules' Code Critic re-flags before the user sees output, but Google never states its tier relative to the implementer. Cognition says only that they're "experimenting with routing the testing phase to different models" — no formal rule. The explicit anti-pattern (never a weaker model reviewing a stronger one) appears genuinely novel.

Per-ticket budget

unshipped elsewhere

Copilot's spending limits (Jul 2, 2026) are org-wide; Devin's dollar quota is account-wide. A per-task budget ceiling wasn't found shipped anywhere.

Dual-audience mode

unvalidated

No competitor targets non-developers on their own existing repos this way. GitHub Spark builds apps from natural language but doesn't do issue-to-PR against a repo you already own. Differentiated, but nobody has proven demand for it yet.

Updated adoption data

The 55% vs. 82.6% figure from the original research is retired. Current best source: a task-stratified analysis of 7,156 agent PRs (MSR 2026 mining challenge) — Codex 77.9%, Cursor 74.5%, Claude Code 71.9%, Copilot 68.0%, Devin 61.6% merge rate. By task type: chore 84.0%, docs 82.1%, feature 66.1%, fix 66.0%, perf 55.4%. The paper does not analyze acceptance against PR size — the variance is driven by task type, not diff size, so Pipenzo's foundational small-PRs thesis remains a design bet, not a proven one. If the size thesis is meant to hold, the diff-size gate should be paired with task-type-aware routing, since task type is what the data actually shows moving the number.
