Research memo — AgentDock downstream product

The Implement Button

An open-source disruptor: a GitHub-issue-to-pull-request agent built on top of AgentDock, small enough on every PR to actually get reviewed.

Scope landscape · stack · pipeline · PR size · UI · model routing Method 10 parallel research agents, frontier model, primary sources License open source
Verdict

Build it, and win on the one axis every competitor is losing on: review burden. Industry-wide, agent PR acceptance sits at 55% against 82.6% for humans and review time rises 441.5% under heavy AI adoption — because every incumbent optimizes for how much an agent can ship, not how cheaply a human can trust it. A near-identical funded competitor, Sweep.dev, discontinued this exact product chasing that same metric.

This app is scoped against the metric that actually matters instead: every PR it opens is small enough to review in one sitting, by construction — gated at the planning step, not chopped after the fact — reviewed first by deterministic tools and a cross-model adversarial pass before a human ever sees it, and usable by a non-developer without ever reading a diff. AgentDock already supplies roughly 60% of the plumbing — worktree isolation, session resume/fork, an approval and audit model — for the rest.

02

The correction — and the real wedge

re-check

A first pass called Alfred "CLI/config-only." A deeper read of its actual source found a signed, six-tab desktop app with a working kanban and approve/decline UI — a direct competitor to the original pitch, not an absence to build into.

Sources: DESKTOP_CLIENT.md, PipelineView.tsx (github.com/luminik-io/alfred)

So "nobody has a UI" doesn't hold. What does hold, on the same close read: Alfred's "team" is a set of role slugs fired by launchd/systemd on fixed cron intervals — it explicitly rejects a persistent orchestrator as a design goal, and its roles never share state across repos. Sortie's own maintainer has stated, in a public discussion, that an interactive UI is not the roadmap.

AgentDock's daemon is already long-lived. That's the wedge that survives scrutiny: on-demand dispatch with live SSE streaming, on a cross-platform Windows-first Electron shell — not "has a UI," but "has a UI backed by a runtime built to stay running," which is structurally outside what either close competitor is aimed at.

03

The stack

AgentDock's apps/desktop has zero UI runtime dependencies today — 1,246 lines of hand-written CSS, no component library. Every pick below was checked against that renderer's actual constraints: a strict CSP (style-src 'self' unsafe-inline', no external script hosts), contextIsolation + sandbox, and a daemon that's esbuild-bundled to one file and run under Electron's own Node ABI — which rules out native addons.

not daisyui

DaisyUI was the starting suggestion. It's ruled out for one specific reason: it hands you CSS classes for markup you still write — it can't manage focus or announce state changes, so the approval dialog (where a non-developer says yes to something irreversible) would need a headless library bolted on anyway. shadcn/ui gives you the component source, owned in-repo, built on Base UI primitives that already solve focus-trapping and ARIA. That's the whole decision: a dual-audience UI is a structural problem, not a styling one — a PM needs one sentence and a button, a developer needs the branch name and the raw diff, and you can't express that difference in daisyUI's class names.

shadcn/Base UI registry components target React 19; AgentDock's desktop is on React 18.3 — tracked upstream as agentdock#106. Approved, with one sequencing condition: primitive components, design tokens, and branding get established first, before any product screen is built against them — not screen-by-screen improvisation.

04

Plan, refine, implement, review

The instinct was to reach for a multi-agent framework — Agency Swarm, LangGraph, CrewAI. All three would duplicate machinery AgentDock's daemon already runs.

no framework

AgentDock's daemon already negotiates session.fork, tracks a durable parent/child subagent graph, and gates every consequential action through one permission policy with a full audit trail. That's the same differentiator LangGraph sells. Adding a second orchestrator on top means two sources of truth for cancellation, permissions, and resume. The pipeline below is a thin state machine inside the daemon, driving scoped subagent definitions — no new runtime.

05

Model routing

The app should route each phase to a model tier by task complexity, not run everything on one frontier model — and orchestrate across providers deliberately, not just within one. AgentDock already wraps Claude and Codex; Gemini is next on its own roadmap. The routing policy below is written as tiers and vendors, not hardcoded model names, so a third provider slots into the same table rather than requiring a redesign. A verification pass found the wire support for this doesn't exist in AgentDock yet.

prerequisite

POST /v2/sessions has no model field today — the schema is .strict() and a caller passing one gets rejected. The internal plumbing to run a specific model exists, but it's fed only from provider auto-detection, never from a request. Filed upstream as agentdock#107: add an optional, validated model field to session creation and resume/fork, and serve the already-declared-but-unimplemented model.catalog capability for real.

PhaseTierDeciding signalEscalation
Refinemid, fixedNever cheapened — the spec is the contract everything downstream is graded againstFails validation → 1 retry same tier; then human
Implement — smallcheapEstimate ≤ 50 LOC, ≤ 2 files, no prior retryGate failure → retry same tier ×1, then ↑1 tier ×1, then human
Implement — standardmidDefault, ≤ 300 LOC / ≤ 8 filesSame ladder, capped at 3 attempts
Implement — hardfrontierAbove standard, or a deterministic override1 retry with telemetry, then human — no auto-escalation
Review — reviewermid, same vendor as implementFixedFindings feed the implement retry, not a new model
Review — adversarial verifier≥ implement's tier, never lowerCross-vendor as a tiebreaker among equal tiers onlyRejects twice → human, verifier itself never escalates

Deterministic overrides force the hard tier before the estimate is even consulted: any prior failed attempt, paths matching security/auth/migration globs, more than 8 files touched, or a priority:high/breaking label. The estimate from the refine phase is the routing signal — a dedicated classifier step was considered and rejected: deployed routers rarely beat an oracle by much, and per-task difficulty often isn't predictable from the prompt alone, which is exactly what the deterministic overrides exist to catch.

Guardrails against slop and hallucination aren't a separate system — they're what this whole pipeline is for. Low quality is caught by the deterministic gates and the tier-up adversarial verifier before a human ever sees it; fabrication is refused at the source — the verification block cites only what a gate actually produced (a real test run, a real diff stat), never an unearned claim, and anything self-reported is labelled as such rather than presented as fact. What's new here: every piece of text the app generates for a human — the drafted issue in Plan, the PR description, the plain-language summary in simple mode — passes a humanizing rewrite pass before it's shown, so it reads like a careful colleague wrote it, not templated AI output. That's a real, separate step in the pipeline (a cheap-tier pass, since it's a style transform, not a judgment call), not a hope that a good prompt handles it.

The verifier rule is deliberately route up, never sideways or down — a 116-task cross-model study found the weaker model reviewing the stronger one caused net regressions (3 fixes, 13 new bugs introduced), while the stronger reviewing the weaker gained +18.1pp. Vendor diversity only breaks ties between reviewers of equal strength. Two more review-quality rules follow from separate evidence: the reviewer session sees only the spec and the diff, never the implementer's own transcript — same-session self-review measurably underperforms a fresh session seeing just the artifact; and tests are generated from the spec by a different pass, never written by the implementer itself, since self-authored tests are contaminated by the code they're meant to check.

09

Build order

Design system, before any screen

Establish shadcn/ui's primitive components, design tokens (color, type, spacing), and branding first — the walking skeleton and everything after builds against this, not around it.

Walking skeleton

Hardcoded repo, PAT from env, no queue, built against the design system above. One ticket through refine (EARS spec + size estimate) → implement → deterministic + adversarial review → react-diff-view screen → Open PR. Proves the loop end to end before anything else exists.

Ticket store + phase machine

JSON-file persistence matching AgentDock's existing store pattern, crash recovery, phase-change SSE, a real ticket detail/progress view.

GitHub & the size gate, properly

Device-flow OAuth (@octokit/auth-oauth-device) in Electron main, token vault, real issue list via @octokit/core, the diff-size/split gate enforced at refine, a test asserting the token never reaches a provider subprocess.

Queue + dual-audience mode + bounded concurrency

dnd-kit kanban, simple/expert toggle with a persisted default, built on the established design system. Multiple tickets queued, one worktree each, respecting the existing workspace-execution lease — and a concurrency semaphore in the ticket orchestrator (default 2, hard cap 4) that serialises any two tickets whose Refine-phase "files likely touched" lists overlap.

Polish

Native notification on HIGH-risk approvals only, a rejection loop that forks implementation again, a dirty-worktree discard path, an audit entry for every publish and every review-gate result.

First post-MVP milestone

gh stack publishing for approved decompositions, then CI-failure auto-fix — one forked attempt, classifiable failures only, re-entering the same human push gate. Both are committed with triggers, not "later" (§11 decisions 06–07).

watch The biggest risk is step 1's temptation to let the agent shell out to gh directly. Keep publishing outside the agent loop from the first commit — retrofitting that boundary later is what breaks the safety property this whole design depends on.

This section originally ended with five committed items and four left at 50/50. It no longer does. Where the plan is genuinely ahead

Refusal as an outcome

still unique

Devin decomposes into stacks at plan time and announces the stack by name, but ships no size thresholds, no refusal condition, and no human approval of the decomposition. Pipenzo's numeric gate (≤100 / 100–400 / >500 lines) with a hard refuse-and-flag branch is still unmatched — the mechanism is commoditized, the policy isn't.

Same-or-higher-tier verifier

undocumented elsewhere

Jules' Code Critic re-flags before the user sees output, but Google never states its tier relative to the implementer. Cognition says only that they're "experimenting with routing the testing phase to different models" — no formal rule. The explicit anti-pattern (never a weaker model reviewing a stronger one) appears genuinely novel.

Per-ticket budget

unshipped elsewhere

Copilot's spending limits (Jul 2, 2026) are org-wide; Devin's dollar quota is account-wide. A per-task budget ceiling wasn't found shipped anywhere.

Dual-audience mode

unvalidated

No competitor targets non-developers on their own existing repos this way. GitHub Spark builds apps from natural language but doesn't do issue-to-PR against a repo you already own. Differentiated, but nobody has proven demand for it yet.

Decisions — nine items, nothing left hedged

The first draft of this addendum committed to five items and left four at 50/50. All nine are now resolved. The four that were open are decided below on one test: does it earn its complexity for a single-maintainer open-source tool running local worktrees on one machine, or is it surface area copied from a funded product with different infrastructure?

06 Concurrencypost-MVP, build step 5In, bounded — not Devin's model. Default 2, hard cap 4, one worktree per ticket. The plan already provisions per-ticket worktrees and AgentDock already holds a workspace-execution lease, so the marginal cost is a semaphore in the ticket orchestrator, not an orchestration rewrite. What Pipenzo does not take on is the expensive half: cloud sandbox fleets, cross-ticket resource scheduling, merge-conflict arbitration between concurrent agents. The real ceiling here isn't architecture, it's one machine sharing one subscription's rate limit. One addition falls out for free: Refine already emits a "files likely touched" list, so two tickets whose lists overlap are serialised rather than run in parallel — a conflict-avoidance property the sandbox-fleet approach doesn't have.
07 CI-failure auto-fixpost-MVP, first milestoneIn, scoped and gated. Trigger: the publish gate and one real PR-open flow working end to end. The deliberate divergence from Jules: the fix commit re-enters the same human push gate. Nothing is resubmitted automatically, because auto-resubmission is exactly the hole the publish gate exists to close.
08 Persistent repo knowledge baseout of scopeOut — and this is a judgment, not a deferral. The measured benefit cited in §04 (+12.2% localisation accuracy, −53.9% completion time) comes from a symbol graph built fresh per session, which cannot be stale. A durable knowledge base adds an index, an invalidation strategy, an embedding store, and a staleness problem whose failure mode is an implementer confidently misled by an out-of-date wiki — worse than having none. DeepWiki and Librarian are indexing products with staff and infrastructure behind them; Pipenzo deliberately has a JSON file store, no DB, and no native addons (§03 rejected better-sqlite3 for precisely this class of reason). The human-gated lesson memory already on the roadmap is the intentional small substitute: append-only, human-approved, no index.
09 MCP integrationout of scope as a Pipenzo featureOut — because it already exists one layer down. AgentDock ships a trusted local-stdio MCP catalog with a route-level approval gate, workspace-trust revalidation, and fail-closed destructive-tool classification (agentdock#85). Any server a user wants is configured at the runtime and inherited; Pipenzo adds no MCP UI and curates no servers. Jules' comparables (Linear, Neon, Stitch) are hosted/HTTP — a transport AgentDock explicitly does not support, so matching them means new runtime transport work, not a Pipenzo feature. And the one integration that matters for this loop, GitHub, is actively contraindicated as an MCP server: it would put the token inside the agent process and break the property §07 rests on — publishing is a daemon-side service the agent process cannot call. One consequence worth noting rather than a gap: because AgentDock's classification is fail-closed, any MCP tool a user does attach lands at HIGH in the risk grading below unless the server declares otherwise, so it inherits the approval UI for free.

The five committed items, specified

Previously these were named as gaps but never designed. Each is now a buildable spec, written against the six screens on the design canvas.

01 · Diff-size gate — refusal as a state, stacks handed to GitHub

MVP

The gate produces two ticket states, not an error, both backed by GitHub labels and both landing in the existing Needs-human lane. pipenzo:needs-pre-scoping — the agent declined; the card shows the estimate, which threshold tripped, and the proposed split, presented as a finished outcome. Nothing retries it automatically. pipenzo:awaiting-stack-approval — a 2–4 PR decomposition is waiting for a human to accept, reorder, or reject; approving materialises one dependency-ordered child ticket per entry, each with its own worktree and branch, and the parent becomes a container card showing 1/3, 2/3 progress. Devin decomposes but never asks; the approval step is the part that stays unclaimed.

Maintenance is delegated, not built. Pipenzo owns the split decision, the ordering, and the human approval of it. GitHub owns base-branch rewriting, restacking after a merge, and the PR-to-PR view, via native stacked PRs and the gh stack CLI — invoked from the daemon-side publish service under the same execFile trust model as git, never as an agent tool. This is a deliberate exception to §03's "not the gh binary" rule and the only one: the API client stays @octokit/core, and gh is runtime-detected and optional. Without it an approved stack still ships, as sequential PRs with an explicit base-branch note. Pipenzo renders the stack as a read-only list linking out to GitHub's own stack view, and never writes a restacker.

02 · Pre-commitment — predict, then be graded on it

MVP

When: before every action graded MEDIUM or HIGH by the classifier in item 05. LOW actions do not pre-commit — the point is a readable signal, not a transcript of every file read. One classifier serves both features.

What the implementer posts, as a structured precommit event, before the action runs: the action verbatim; expect — one sentence predicting the outcome ("the three new cases in provider-caps.test.ts pass, nothing else changes"); if_wrong — what it will do if the prediction fails. The real result is appended afterwards as a paired outcome event and diffed against the prediction into a match / partial / mismatch verdict.

In the event stream (TicketDetail → Activity): the prediction lands first as its own row, marked predicted. When the outcome arrives the pair collapses to a single row carrying matched or mismatched. Mismatched pairs never auto-collapse. This is the part worth having: pre-commitment is usually an internal anti-fabrication trick, and exposing the mismatch count turns it into something a reviewer can act on — the PR body's confidence line degrades when it is non-zero ("the agent's own predictions were wrong twice during this run"), Simple mode says the same in plain language, and each mismatch feeds the cumulative-risk counter. An agent whose predictions are going wrong gets checked on sooner, automatically.

03 · Screenshot verification — legible, and still not proof

MVP

How it is captured: Playwright, driven by the daemon, using the target repo's own installation. Pipenzo ships no browser and detects the capability rather than providing it — if the worktree has @playwright/test and a dev or preview script, the verification phase runs a short capture script generated from the spec's EARS clauses (start the dev server on an ephemeral localhost port, navigate, capture, tear down). Repos without Playwright can set a pipenzo.verify.screenshot command that emits PNGs to a directory. Neither available means the evidence block says so — there is no fallback and nothing is faked. Two rejected alternatives, for the record: the agent driving a browser itself (arbitrary network egress inside the agent process), and Electron's own webview (running the target app inside the renderer that holds the token vault and the hardened CSP — a real security regression, not a shortcut). A baseline capture on the base commit before implementation gives a genuine before/after pair, which is what makes the screenshot mean something rather than decorate.

Where it renders: DiffReview's existing Verification block gets a thumbnail strip, each shot captioned with the EARS clause it was captured for plus URL, viewport, and commit SHA. Simple mode makes it the hero — the before/after pair above the plain-language summary, because for the non-developer audience this is the evidence. The PR body carries the same images with the same captions.

How it stays honest: a screenshot feels like proof and isn't — the agent chose the URL, the state, and the moment. So the verification block splits into two visually distinct zones that are never merged into one list: machine-verified (build, typecheck, spec-generated tests, gitleaks, Semgrep — results the app produced) and agent-captured, self-reported (text evidence and every screenshot). Each shot carries a fixed provenance line rather than a subtle badge — "captured by the agent, showing what it chose to show" — with the capture script expandable beside it, and the script itself appears in the diff so a human can see what was actually photographed. Hard rule: a screenshot is never an input to a pass/fail decision. It buys legibility, not trust.

04 · Kiro reconciliation — a docs fix, and it is finished

no UI impact

Confirmed against the canvas: no artboard claims EARS or spec-driven development as a Pipenzo invention, so there is nothing to remove from the UI. The change is prose only, in the README and in this report — the Refine step is no longer presented as a differentiator, because Kiro has shipped requirements/design/tasks specs with property-based verification as a GA AWS product since May 2026 and Pipenzo's Refine is a subset of that. What is genuinely additive is narrower and gets stated instead: the refine subagent is read-only by construction (Read/Grep/Glob — no write tool exists in its definition, so it cannot start implementing while it is still deciding whether the ticket is sane), and it emits a numeric diff-size estimate that a refusal policy is enforced against. One forward guardrail: onboarding and empty-state copy, when it gets written, must not re-introduce the claim.

05 · Risk-graded approval, with cumulative risk

MVP

Three levels, classified per action, replacing the single approve/reject card:

LOW Reversible, inside the owned worktree, no network, no secrets — reads, greps, edits to source under the worktree, running the repo's own build and test commands. Auto-proceeds. No card, no notification, one passive line in the Activity stream. This should be roughly 95% of actions; if it isn't, the classifier is wrong.

MEDIUM Reversible but consequential, or outside the obvious blast radius — adding a dependency, running a script not declared in the repo's manifest, writing outside the source tree (lockfiles, CI config, .github/), deleting files, rewriting local history, network egress for a package fetch. Blocks on a compact inline card in the Activity stream: approve, or reject with a reason. Requires a pre-commitment record. No OS notification unless it has been waiting more than 60 seconds. The Undo affordance already on the approval screen applies here.

HIGH Irreversible or off-machine — anything AgentDock classifies external_side_effect (push, open PR, comment on the issue), paths matching the security/auth/migration globs already used for tier override in §05, force-push, deleting outside the worktree, writing a credential-shaped string, and any MCP tool not explicitly declared safe. The full approval card, OS notification, mandatory reason on reject. The existing rule is unchanged and unchangeable: no persistent auto-allow exists for external_side_effect at any risk level, and Undo does not apply — once approved it has left the machine.

Cumulative risk — yes, and it is the interesting half. OpenHands' actual insight is that risk compounds across a session even when every individual step is fine, so the counter tracks unreviewed accumulation rather than total severity: each auto-approved LOW action adds 0.1, each MEDIUM approval adds 1, each pre-commitment mismatch adds 2, and a HIGH action adds nothing (a human already looked hard at it). Any approval a human gives resets it to zero. When the score crosses the threshold (default 10), the next MEDIUM action is promoted to HIGH — full card, notification — and the card states why: "14 low-risk actions since your last look." It renders in TicketDetail's right rail beneath Budget and Subscription headroom, in the same visual language: a segmented bar reading ok → building → check in. It is a "since you last looked" meter, not a threat gauge.

Updated adoption data

The 55% vs. 82.6% figure from the original research is retired. Current best source: a task-stratified analysis of 7,156 agent PRs (MSR 2026 mining challenge) — Codex 77.9%, Cursor 74.5%, Claude Code 71.9%, Copilot 68.0%, Devin 61.6% merge rate. By task type: chore 84.0%, docs 82.1%, feature 66.1%, fix 66.0%, perf 55.4%. The paper does not analyze acceptance against PR size — the variance is driven by task type, not diff size, so Pipenzo's foundational small-PRs thesis remains a design bet, not a proven one. If the size thesis is meant to hold, the diff-size gate should be paired with task-type-aware routing, since task type is what the data actually shows moving the number.
