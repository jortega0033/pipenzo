Model routing — a routing class picks a model tier

A routing class is a phase of work. A model tier is a model's strength, cheap through frontier. The kanban lanes are a third, unrelated thing. Pipenzo brings no models and no inference credits: it runs whatever agentdock has authenticated, as local subprocesses under your own login. So the tier a class picks is the setting on this page — which model a tier resolves to is the provider's.

A tier floor is a floor, not an override: a deterministic override above still forces frontier, and a size estimate can still push a chore up a rung. Nothing here can lower a tier, and nothing here relaxes the five deterministic gates — strictness only ever adds.

Deterministic gates — the hard, non-negotiable set

These five run first, on this machine, and either pass or block the ticket. Only after all five pass does the LLM review pass run, in a fresh session seeing just the spec and the diff, followed by the separate adversarial verifier. There is no configuration that turns one off — which is why they render as switches you can read but not move.

{{g.name}}{{g.sub}} always on
In the diff view these render as the Machine-verified block, where gitleaks and Semgrep report on one line — the same five, grouped for reading rather than for configuring. Nothing else joins that block: a repo's own lint runs in its CI and can move a ticket to pipenzo:ci-failed, but it is not one of pipenzo's gates and never appears in the gate count.
Two rules that keep the test gate honest A failing spec-generated test is not automatically the code's fault. It is adjudicated once, by the verifier tier, into test-wrong or code-wrong. A test ruled invalid is dropped with the ruling recorded in the evidence block, never silently deleted, and the drop is visible in the PR body. The diff-scope check measures implementation files only. Generated tests are counted and reported separately, so a large generated test file can never blow a ticket's size estimate on its own.
